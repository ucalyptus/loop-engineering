The comparator is usually the weak part

A controller is only as good as its error signal.

loopctl: one round, six steps

Part 3 · Production
Turn your pipeline into a loop
name = "fraud-model" goal = "Retrained model passes eval; serving config is valid." actor = 'claude -p --permission-mode acceptEdits "$(cat)"' fresh_clone = true checks = [ # sensors you already run in CI { name = "unit", run = "pytest -q" }, { name = "lint", run = "ruff check ." }, { name = "data", run = "python validate.py data/" }, { name = "quality", run = "python eval.py --min-auc 0.85" }, { name = "k8s", run = "kubeconform -strict deploy/" }, { name = "infra", run = "terraform validate" }, ] admission = [ # gates on every proposed change { name = "allowlist", run = "! git diff --cached --name-only | grep -vE '^(src|deploy)/'" }, { name = "secrets", run = "gitleaks protect --staged" }, ] [limits] max_iterations = 20 # rounds max_actor_seconds = 1800 # agent time budget max_diff_lines = 150 # one small change per round
Template: replace the commands with your own
Your CI checks are the sensors.
Admission gates are policy: an allowlist of paths, a secrets scan.
Limits are the governor: rounds, agent time, diff size.
Start with the checks you already trust. Add one sensor each time the loop fools you.

Appendix · Failure modes
Four ways a loop fails
Oscillation
The agent undoes and redoes one change.
Fix: detect repeated states, limit steps.
Drift
Small errors add up over many steps.
Fix: compare to the spec, not the last step.
Goodhart
The loop meets the metric, not the goal.
Fix: mix checks, keep a slow judge on top.
Sensor blindness
The real error is not in the observed state.
Fix: widen what the loop sees first.
Loop engineering is cybernetics · 30
Appendix · The key property
Level-triggered, not edge-triggered
Edge-triggered
The system reacts to events. If it misses one event, its picture of the world stays wrong.
Level-triggered
The system reads the full current state each time. A missed event does not matter. The next loop fixes it.
Agents need the same property. Each step must read the world again. It must not trust its own memory of the world.

Appendix · Where the frontier model sits
Frontier models are the actuator
Opus 5.5 and Fable 5.1 do the work. They plan, write code, call tools and draft text.
This is the part of the loop that needs generation. It is also the most expensive part per step.
A good actuator needs
  • Reliable tool use
  • Long context for state
  • Good recovery after an error
The weak point
We often use the same model as the comparator too.

Appendix · Rule 1 of 4
Declare the setpoint as data
If the goal is only prose, no sensor can measure the error.
From Kubernetes: declarative spec
In practice
  • Write acceptance criteria as checks.
  • Keep the spec in a file. The loop reads it at each step.
  • Say what you want, not how to do it.
Loop engineering is cybernetics · 36
Appendix · Rule 2 of 4
Build sensors before actuators
An agent cannot fix what it cannot observe.
From Kubernetes: observed status
In practice
  • Give the loop fresh reads: diffs, test output, API state.
  • Read the state again at each step.
  • Log each observation, so you can replay a run.
Loop engineering is cybernetics · 37
Appendix · Rule 3 of 4
Make every action idempotent
Loops retry. A retry must not double the damage.
From Kubernetes: idempotent actions
In practice
  • Use upserts and keys, not blind creates.
  • Plan first, then apply, with a dry run.
  • Put actions you cannot undo behind a human gate.
Loop engineering is cybernetics · 38
Appendix · Rule 4 of 4
Add a governor: limits and back-off
A loop without a stop condition is a cost leak.
From Kubernetes: back-off and requeue
In practice
  • Set a maximum for steps, tokens and time.
  • If the same diff comes back two times, stop.
  • On external errors, wait longer before each retry.

Appendix · The decider
The scheduler picks, the kubelet runs
Kubernetes scheduler
  • filter: which nodes can run this pod?
  • score: which one is best?
  • pick: one node gets the pod
Same split for agents
  • a small, fast model decides
  • a big, slow model does
  • the checks judge
# [decider] asks Jev two typed questions per round move ∈ {act, ask_human, stop} target ∈ failing checks # asked 3 times; confidence = # lowest p of the agreed move
Guardrails: the decider cannot judge pass or fail, and cannot pick a passing check. Under 60% confidence, or if the three answers disagree, a human decides. If the decider fails, loopctl uses the built-in rule.
